# Day 4 - Structured Validation and API Automation Pipeline

## 1. Objective

Day 4 converted the runtime validation work from Day 3 into structured, machine-readable engineering output that can be consumed by automation and later CI.

The implemented pipeline is:

AI Chase C++ Runtime -> ValidationResult -> ValidationResultCollector -> JSON -> Python Contract Validation -> FastAPI -> Playwright API Automation

The purpose is to move beyond on-screen diagnostics and make runtime validation results externally consumable, testable and suitable for automated quality gates.

## 2. Structured Validation Result Model

A generic ValidationResult model was introduced so runtime validators can report results without coupling the result format to one specific subsystem.

Each result contains:

- validatorId
- entityId
- status
- message
- timestampSeconds

ValidationStatus currently supports PASS and FAIL states.

The model is intentionally generic so future validators such as pathfinding, delivery, collision, timeout and scenario validators can use the same reporting infrastructure.

## 3. Validation Result Collector

ValidationResultCollector stores validation events and provides summary information including:

- total result count
- pass count
- fail count
- whether any failures exist
- ordered access to collected results

The collector can also be cleared when a new gameplay session starts.

## 4. JSON Serialization

ValidationResultJsonWriter converts collected validation results into a structured JSON document.

The current schema contains:

- schemaVersion
- summary
- results

The summary contains total, passed, failed and hasFailures values.

Each result contains validatorId, entityId, status, message and timestampSeconds.

The serializer also handles the special characters currently covered by the regression suite, including quotes, backslashes, newlines, carriage returns and tabs.

## 5. Production Runtime Integration

TutorialGame now owns a ValidationResultCollector and tracks active gameplay validation time.

When StartGame begins a new session:

1. Previous validation results are cleared.
2. validationElapsedTime is reset to zero.
3. A fresh validation_results.json artifact is written.

The validation timer advances only while gameplay is active.

The Day 3 stuck-agent validator was integrated with the structured result pipeline.

A new AI_STUCK failure is recorded only on a false-to-true stuck transition. This edge-triggered design prevents the same continuously stuck enemy from generating duplicate failure records every frame.

When a new AI_STUCK incident is recorded, the JSON artifact is immediately rewritten so the failure is persisted.

Human-facing enemy identifiers use values such as Enemy_1 rather than zero-based internal indexes.

## 7. Python Validation Processor

Automation/validation_processor.py validates the JSON contract before downstream automation consumes it.

The processor validates conditions including:

- file existence
- valid JSON syntax
- object root structure
- supported schema version
- required summary and results structures
- required result fields
- valid PASS or FAIL status values
- valid timestamp types
- summary total consistency
- pass and fail distribution consistency
- hasFailures consistency

Python regression result:

17/17 tests passed.

## 8. Local REST API

A FastAPI service exposes validation information to external automation.

Implemented endpoints:

- GET /health
- GET /validation/results

/health reports whether the API is operational.

/validation/results reads and validates the configured validation result artifact before returning it.

Verified response behaviour includes:

- HTTP 200 for valid validation data
- HTTP 404 when the result file is missing
- HTTP 422 when the validation artifact is malformed or violates the expected contract

The validation result path can be configured through VALIDATION_RESULTS_PATH.

## 9. Playwright API Automation

Playwright is used for API-level automation rather than browser UI automation at this stage.

The Playwright suite automatically starts the FastAPI service and verifies:

1. The health endpoint returns HTTP 200 and the expected operational response.
2. The validation results endpoint returns HTTP 200 and validated result data for a controlled valid fixture.
3. The validation results endpoint returns HTTP 404 when the runtime result file is missing.
4. The validation results endpoint returns HTTP 422 for malformed JSON.

No browser binaries are required for the current API-only Playwright suite.

## 12. Generated Artifact Handling

Generated and environment-specific files are excluded from source control, including:

- .venv/
- node_modules/
- playwright-report/
- test-results/
- __pycache__/
- *.pyc
- ValidationResults/
- Automation/tests/runtime/

Controlled Playwright fixtures remain source-controlled because they are deterministic test inputs rather than generated runtime output.

## 13. Engineering Decisions

The validation result model was kept generic instead of embedding AI-stuck-specific metrics into the shared contract.

The existing nlohmann JSON header used by the GLTF subsystem was not reused as a project-wide dependency. A small dedicated serializer was introduced for the validation layer instead.

Runtime AI_STUCK events use edge-triggered persistence to prevent duplicate per-frame failure records.

Playwright was selected for API automation so the same automation technology can later expand into broader tooling or web-based validation interfaces if required.

## 14. Day 4 Outcome

Day 3 established runtime detection and defect investigation.

Day 4 converted those runtime validation capabilities into structured automation infrastructure.

The project can now produce machine-readable validation results, validate their contract in Python, expose them through a local REST API and verify API behaviour automatically with Playwright.

This provides the foundation for Day 5 CI and containerisation work, where the validation pipeline can be executed automatically through Jenkins and Docker.
